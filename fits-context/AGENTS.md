### Git Workflow & BMad Execution Protocol (Mandatory for All Agents)
All AI agents must follow this 9-step lifecycle for every Story or task:
1. **Status Check & Sync**: Use BMad v7 `_bmad-output/initiative-fits/tickets.toml` and ticket-linked story plans. Read status with `uv run _bmad/method/scripts/tickets.py --project-root . status _bmad-output/initiative-fits`; mark the story `in-progress` via `tickets.py mark`. `_bmad-output/initiative-fits/archive-v6/sprint-status.yaml` is frozen history; do not recreate `implementation-artifacts/sprint-status.yaml`.
2. **Issue Context Loading**: Load the GitLab Issue via `glab issue view <id>` (Issues #1 to #33). Extract Acceptance Criteria (`Given/When/Then`) and design links.
3. **Branching**: Branch off latest `main`: `git checkout -b <type>/#<issue-id>-<short-slug> main` (e.g. `feat/#7-deterministic-bgid`). Never commit on `main`.
4. **Implementation & Tests**: Implement code strictly matching PRD and `mockui-master.html`. Add unit/integration tests in `backend/Fits.Tests/` or `frontend/`, plus QA e2e tests covering the story's Given/When/Then acceptance criteria (`bmad-qa-generate-e2e-tests`) — e2e coverage is mandatory per story (hard gate at step 8).
5. **Regression Verification Gate**: Verify tests pass green (`dotnet test` via Harbor Docker SDK image if local SDK missing, `npm run build`).
6. **Conventional Commit**: Commit with issue reference: `git commit -m "<type>(<scope>): <desc> (#<issue-id>)"`.
7. **Merge Request & Review Gate**:
   - Push branch and create MR with an itemized, comprehensive description covering each requirement in the issue list. Note: GitLab Push Options overwrite repeated `-o merge_request.description` flags, and Git forbids literal newlines. Markdown block elements (`###`, `- `) fail to render after `<br>`. Therefore, use standard semantic HTML tags (`<h2>`, `<h3>`, `<p>`, `<ul>`, `<li>`, `<strong>`, `<code>`) in a single push option so GitLab renders rich, beautiful markup:
     ```bash
     git push origin <branch-name> \
       -o merge_request.create \
       -o merge_request.target=main \
       -o merge_request.title="<type>(<scope>): <summary> [skip-version]" \
       -o merge_request.description="<h2>Summary</h2><p>Closes #<issue-id></p><h3>Requirements &amp; Scope Addressed</h3><ul><li><strong>Requirement 1</strong>: <what was done></li><li><strong>Requirement 2</strong>: <what was done></li></ul><h3>Implementation Details</h3><ul><li><strong>Backend</strong>: <details></li><li><strong>Frontend</strong>: <details></li></ul><h3>Verification &amp; Tests</h3><ul><li>Backend: X/X tests passed</li><li>Frontend: Y/Y tests passed</li></ul>"
     ```
   - Mark the ticket `in-review` via `tickets.py mark` in its story plan.
   - Announce review tier (HIGH/MEDIUM/LOW) and await Human Approval in chat.
8. **Automated CLI Merge**:
   - **QA e2e Gate (hard rule)**: a story MR must include generated, passing e2e tests for its acceptance criteria before it may close the story — no e2e, no `done`: hold the merge or reopen the issue and track the gap.
   - Upon human approval in chat, run: `glab mr merge <MR_ID> --no-squash --remove-source-branch --yes`.
   - Mark the ticket `done` via `tickets.py mark` in its story plan. Verify the GitLab issue is closed.
9. **Deploy & Tag (MANDATORY after EVERY merge — no exception, docs-only included)**:
   - `git pull --ff-only origin main && docker compose up -d --build` — the compose stack is the single test/deploy surface; verify at `http://localhost:8080` (production build + same-stack `/api` proxy). Do not use ad-hoc dev servers as the verification entrypoint.
   - **Only from this checkout, and only for `main`.** A `docker compose -p fits up -d --build` run from another working tree replaces `fits-api` and `fits-web` on :8080 with a build of that tree (the container names are fixed and the project is `fits`): it happened minutes after release 0.20.0 and left :8080 on another branch's uncommitted code. To run any other tree or branch, use an isolated project: its own `-p` name, its own container names (an override file) and its own `PORT`, `API_PORT` and `POSTGRES_PORT` (an `--env-file`); check it with the `FITS_*` variables of `scripts/verify-compose-pod.sh`; remove it when done (`down -v --rmi local`).
   - Or run `scripts/release.sh <minor|patch|none>` which does bump+commit+deploy+tag+push in one command (preferred; see `docs/GIT_WORKFLOW_BMAD.md` §6).
   - Bump `VERSION` (repo root, mirrored in `frontend/package.json`) from the merged MR's dominant commit type: `feat:` → MINOR, `fix:` → PATCH, `docs:/chore:` → PATCH only if other versions shipped since its last tag. Keep `0.x.y` until the first production release decision (`1.0.0`).
   - `git tag -a <version> -m "<type>: <summary> (#<issue-id>)" && git push origin main --tags` — tag name is the bare `VERSION` string (e.g. `0.8.1`), **no `v` prefix** (rule change 2026-09-30; old tags `v0.2.0`–`v0.8.0` keep their prefix, new tags from `0.8.1` onward are bare). Never move/delete an existing tag — rollback is `git checkout <previous-tag> && docker compose up -d --build`.
   - Full rules: `docs/GIT_WORKFLOW_BMAD.md` §6 (Release & Tagging).

### Hard-Learned Standards (do NOT repeat these mistakes)
1. **Brand assets single-source**: TCB logo comes from `public/logo.svg` via `<img>` — NEVER inline-copy SVG paths into JSX (a pasted copy was silently clipped to 10/18 elements and shipped broken). When fixing an asset bug, grep ALL placements (`grep -rn "logo" frontend/src/`) and fix every one in the same commit; screenshot every screen where it appears after rebuild.
2. **Tests green ≠ UI correct**: before claiming any UI change done, rebuild the compose web (`docker compose up -d --build web`) and verify in a real browser at `http://localhost:8080` — exercise the flow, screenshot it, check DOM (images `naturalWidth>0`, toggles' computed display) and the network tab (403s hide behind generic error text). Unit tests assert behavior in isolation; they cannot see the deployed bundle or env-config interactions. Note: `up` waits for the API's health check (#131), so while the API is unhealthy that command fails and leaves web created but not started; recover with `docker compose up -d --no-deps web` (add `--build` after a frontend change).
3. **Server-side is the security boundary**: frontend flags (`VITE_ENABLE_DEV_AUTH`) are UI toggles, not auth gates. Gating identity headers on them broke login (403) — the `X-User-Name` header must be validated server-side only (see `Program.cs` middleware + `ProductionRejectsDevelopmentHeader` test); never "fix" auth by client-side gating alone, and never ship a credential-looking field that the server does not validate.
4. **OpenShift pods are not compose containers, so compose is made to behave like one**: the platform runs images as an arbitrary UID (group not 0) with a read-only root filesystem, only `/tmp` writable, port 8080, and configuration only from ConfigMap/Secret environment variables. The compose stack now applies the same constraints to api and web (uid:gid `1000680000:1000680000`, read-only root, `/tmp` tmpfs, capabilities dropped, the web image on its own defaults, API and Postgres on `127.0.0.1` only; #131), so a pod-only crash like #127 shows at `http://localhost:8080` too. Keep that parity: a change to the pod-relevant parts of `docker-compose.yml` must keep `tests/test-compose-pod.sh` green and be re-checked with `scripts/verify-compose-pod.sh`. What compose still cannot show: the file modes of the Jenkins checkout (0660 there, 0644 on a Mac), Production authentication (compose runs `Development` with mock users), the attachments PVC permissions (compose runs a one-shot `chown`, #129), and Kong/Route/ArgoCD/the real database. Files copied into an image must be world-readable whatever mode the checkout left on them: with a non-zero GID only the "other" bits count, and this crashed the first NPD deployment (#127); `scripts/verify-ocp-images.sh` reproduces those modes. The Jenkins/AWX pipeline builds from the repo root with literal `FROM` lines and the Nexus NuGet proxy, and gates stable tags on Trivy; keep those conventions in every Dockerfile. Before touching a Dockerfile, an entrypoint script, nginx config, a port, an environment key or file storage, read `docs/OPENSHIFT_GITOPS.md`, and re-run its pod-constraint recipe afterwards. Edit only the inputs of the manifest repo (`gitops/it-admin/fits_manifest`); never put a secret value in git or in a ConfigMap.
5. **MR Description is a mandatory contract, never bare `Closes #ID`**: An MR without an itemized breakdown of what was actually implemented against each requirement/issue list is considered incomplete and rejected by Tech Lead. Always use multiline push options (`-o merge_request.description="..."`) to structure: (1) Problem / Requirements Breakdown, (2) Detailed Code Changes by File / Component, (3) Verification & Test Evidence (test counts, build time). Never leave description empty or a 1-line stub.
6. **Committed and paid money lives in two places; read it through `LedgerTotals`**: the PO ledger (`po_bookings`: no invoice = PO issuance, invoice = actual spend) and the item columns `committed_amount_thb` / `paid_amount_thb`. `PoBookingService` bumps both in one transaction, but a seed, a script or an old booking can leave the column behind, and a reader that trusted the column showed THB 0.00M committed beside a ledger holding 13.70M (and the PO funds check let a THB 2.0M booking through over THB 1.0M of true remaining). Every reader that shows or guards committed or paid money uses `LedgerTotals` (`backend/Fits.Api/Services/LedgerTotals.cs`: the larger of column and ledger); a script that writes `po_bookings` must also update the item columns (see the end of `scripts/demo-seed.sh`). The budget-cut floors (`BudgetCutService`), the amount guard (`BudgetAmountGuard.ViolationAsync` / `BelowCommittedAsync`, which every writer of an estimate calls after it has locked the item) and the selective export (`SelectiveExportService`) use it too (#140): do not read `CommittedAmountTHB` directly for a decision or a figure. The shell's per-BGID totals are summed from the ledger rows already.
7. **Keyboard focus is judged by what a person sees, and every overlay owns its focus**: a ring that `getComputedStyle` calls solid and 2px can still sit under the sticky top bar, under a drawer, or outside a scrolling frame, and a walk that reads only the ring passed with 52 of 231 stops under the top bar (#149). Use `frontend/e2e/focus-walk.ts` (hit-test with `elementFromPoint`, measure against every clipping ancestor and the window, Tab AND Shift+Tab, wait for the smooth focus scroll to end) for any new overlay, frame or sticky element. A dialog, popover or drawer takes focus when it opens, keeps Tab inside (`frontend/src/utils/focusTrap.ts`, or an `inert` page behind it as `useMenuDrawer` does for the phone menu; one gap is open: after a click on plain text above the first control, Shift+Tab can still leave a dialog, and `tabindex` on the dialog box is not the fix because it sends PageDown to the page behind, see `docs/reviews/focus-gaps-2026-10-06.md`) and gives focus back to what opened it; a file input is never reachable only through a label around a `display: none` input (use a button that opens it). Measured in Chromium, so do not rediscover it: a focused control that already has 32px or more in view is NOT scrolled to (a wide table keeps it half outside its frame: use `clearPinnedPanes` on the frame); focusing a control of the sticky top bar scrolls the page when the window has a `scroll-padding-top` (it centres the bar's control in what is left: 454px a press), so the room for the bar is a `scroll-margin-top` on the page content only (`:where(.content) *` in `fitsCanvas.css`) and a `focus()` on a sticky control uses `preventScroll`; a button that inherits `visibility` from a drawer refuses `focus()` while a `transition: all` still holds it hidden (name the properties or add `visibility 0s`: that was the "frame or two" after a drawer opened, not a Chromium quirk); a scroll frame with nothing focusable inside it is a Tab stop of its own, so a Tab wrap must leave a stop it does not list to the browser (see `wrapTab`); and a radio group counts every radio in `wrapTab` where the browser counts one, so a container should not start or end with one. A dialog opened from another dialog (the Budget Admin override dialog from the item dialog) sits outside it in the page: it takes focus, traps Tab and handles Escape itself, and the dialog under it ignores Escape while it is open (focus can be on the page: a Save that disabled its own button). A click on plain text leaves keyboard scrolling in the dialog body rather than scrolling the page, and Escape closes only the topmost dialog (each dialog listens on window and ignores the key while another sits over it); and a dialog that the markup puts inside the page content takes the content's `scroll-margin-top` off again (`:where(dialog, [role="dialog"], [role="alertdialog"]) *`). A walk that reads the ring and hit-tests every stop does not see that the page moved or that the controls after a stop are skipped: also assert `scrollY` where focus enters a sticky element, and that Tab reaches the last control (the footer buttons) of a dialog. The ring itself stays the one rule in `fitsCanvas.css` (see DESIGN.md, Focus Ring Accessibility): a component changes `--focus-ring-*` tokens and never writes its own outline.
8. **Phones (<= 768px) are supported: a table where a decision is taken has a card layout, and no control may exist only at desktop widths**: the Approval Queue and the Executive Decision Table are lists of cards in windows 768px or narrower and on touch screens narrower than 1024px (`useMediaQuery(COMPACT_LAYOUT_QUERY)`, `frontend/src/shell/useMediaQuery.ts`). The row and the card are built from one set of render helpers with the same test ids, 44px touch targets and 12px gaps; the floating bulk bar rests at the end of the list while keyboard focus is in it, and the sticky top bar's height is the token `--topbar-height`, which the `scroll-margin-top` of the page content (rule 7, never a `scroll-padding-top` on the root) uses to keep focus clear of the bar (WCAG 2.2, 2.4.11). The top bar fits from 320px (the phone bar: menu, search, notifications, profile and sign-out as 44px controls; Help is a menu item there), and the language switch is `#langToggle` in the top bar from 701px and `#langToggleMenu` in the menu drawer up to 700px (#148): e2e specs choose the language with `setLanguage()` (`frontend/e2e/helpers.ts`), which uses whichever is on screen, and never assume `#langToggle` is on a phone. A table that scrolls inside its frame is not a phone layout. Before calling a layout change done, measure the page's sideways overflow (`document.documentElement.scrollWidth - clientWidth`) and hit-test the controls (`elementFromPoint`) at 320, 360, 390 and 768px in both languages, on a loopback Vite server whose API proxy has every write aborted.
9. **A notice is judged by whether it can be read, not by whether it is in the DOM** (MR-D1, 2026-10-06): the shell's toasts have `z-index: 80` and the item dialog and its backdrop 9999, so a toast raised while a dialog is open is drawn under it. The first version of the "back with the Dept Head" notice was a toast; its test asserted the text and passed, and only the picture showed it blurred under the backdrop. A notice that belongs to an open dialog is shown in the dialog (`ItemDetailDrawer`'s `notice` prop); a toast is for what happens after the dialog has closed. Any e2e test of a notice asserts that it is on top (`document.elementFromPoint` at its centre lands inside it) and fully inside the window, and the picture is looked at before it is committed.

### Common Patterns
- 6-Stage Governance Lifecycle (see `_bmad-output/initiative-fits/prd-fits/prd-fits.md`):
  1. **Stage 1 (Request & Item Creation)**: Requester (`chris`, `priya`) drafts new items, imports Excel, or duplicates/pushes previous year items (Single/Multi/All). Multi-category, Capex/Opex, 4 Strategic Classes (`BAU`, `BU New`, `BU New Project`, `Project Carry Over`), quote attachments.
  2. **Stage 2 (Team Lead Review)**: Team-scoped review by Dept Head (`infrahead`). Approve -> Stage 3; Send Back with Reason (status `Returned`, editable by requester); Reject with Reason (status `Rejected`, locked for normal edits with Admin Reopen exception).
  3. **Stage 3 (Budget Admin Screening)**: Central screening by Budget Admin (`admin`). Accounting/GL validation, Budget Admin override with audit log, cross-team duplicate detection, batch package consolidation (11 IT teams), universal reopen from any status.
  4. **Stage 4 (Top Management Approval)**: CEO/CTO Dashboard review, historical comparison & abnormal gap detection, portfolio envelope approval & budget cut trigger.
  5. **Stage 5 (Budget Cut & Allocation)**: 4-Tier Priority Waterfall (Tier 1: `BAU` & Tier 2: `Carry Over` Min 90% allocation floor / 0–10% cut; Tier 3: `BU New` 0–30%; Tier 4: `New Project` 0–100% cut first). Simulation Scenario engine.
  6. **Stage 6 (Export & Actual Spend Tracking)**: One-click Excel export for ERP Dynamics 365, PR/PO commitment and actual payment tracking, real-time remaining budget dashboard.
- Dev auth = `X-User-Name` header (Mock) or cookie session; prod = ADFS/JWT bearer. Frontend `api/client.ts` sends the header.

### Common Pitfalls
- **Mockup Screenshot Automation (`loginOverlay`)**: `_bmad-output/initiative-fits/ux-budget-management/mockui-master.html` has an enterprise login overlay (`login-screen-overlay`, `z-index: 9999`). Any headless browser script MUST invoke `handleSsoLogin()` before capturing views, otherwise all screenshots will duplicate the login overlay.
- **Screenshot Cryptographic Uniqueness Gate**: Always verify that captured assets in `docs/assets/` have 100% distinct MD5 checksums (`md5 docs/assets/*.png`). Never allow duplicate hash output.
- **Modal DOM Isolation**: In `mockui-master.html`, all `.modal-backdrop` containers must be siblings directly under `<body>` with matching closing `</div>` tags. Never nest modals inside another modal.
- **Decisions the decider cannot undo ask first**: an approval cannot be taken back by the approver (only a Reopen by the Budget Admin can, and it returns the item to Draft), so every approval and the portfolio sign-off pass `ConfirmDecisionModal` (`frontend/src/components/`; `role="alertdialog"`, focus on Cancel, rows frozen when it opens, exact total from `sumTHB` in `money.ts`, `null` = unknown, shown as `THB —`) and reports approvals through `ApprovalOutcomeBanner` (stays until dismissed); the executive sheets compare the figures at confirm time and then send the versions and figures they showed (`stamps` on `POST /api/executive/decide`: one per BGID, each with `ifMatchUpdatedAtUtc` present (null = the item had no version), or left out (an empty list is a 400), anything else is a 400; `expected*` on `POST /api/executive/signoff`, money compared within half a satang; #141), so the server refuses a decision taken on a screen that is out of date. The sign-off records the figures as the server read them in that call (separate READ COMMITTED reads, not a snapshot: the audit chain refuses REPEATABLE READ and SERIALIZABLE callers). The cap it records is always the configured `exec.board_target_cap_thb`: the sign-off request has no cap field (a body naming `boardTargetCapTHB` is a 400), the caller's `expectedBoardTargetCapTHB` is only compared with the configured cap, and the setting is changed only by an ADMIN through the audited Settings write (`PUT /api/settings`: one hash-chained `SETTINGS_UPDATE` record per changed key), which takes at most 2 decimals. Never reintroduce one-click approval or a self-dismissing toast for a decision. Row actions carry the BGID in their accessible name (`อนุมัติ 26INFRA041`), so e2e specs match them with `name: /^(Approve|อนุมัติ) \d{2}[A-Z]+\d+$/`, never the bare word.

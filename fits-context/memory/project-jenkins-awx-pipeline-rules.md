Deploy to OpenShift is done by Jenkins `It-admin/Fits/Fits-DEV-Pipeline-CI` -> `Fits-AWX-Pipeline` (AWX template "Docker Build Images v3") then `Fits-DEV-Pipeline-CD` (ArgoCD, Kong, Vault). No manifests live in this repo; they are generated from `gitops/it-admin/fits_manifest` `project.json` (owned by DevOps, Kwanpirom).

Rules learned from failures:
- Service name in project.json must match the Dockerfile's directory: `Fits.Api` -> `backend/Fits.Api/Dockerfile`; `frontend` -> `frontend/Dockerfile` (a typo `frondend` broke CI; CD/Kong requires exactly `frontend`). Framework values: `dotnet`, `nodejs`.
- Build context is the REPO ROOT, so COPY paths are `backend/Fits.Api/...` / `frontend/...`; root `.dockerignore` applies.
- Dockerfile FROM lines must be literal (no `ARG` indirection) or the role cannot read the dotnet/node version. Bank pattern: `...base-image/dotnet/sdk:10.0-alpine AS build`, node as `...base-image/node/node:20-alpine AS base`.
- Restore through Nexus: `dotnet nuget add source -n nuget.org-proxy https://nexus.npd.tcbank.local/repository/nuget-group/index.json` + disable nuget.org.
- Backend final stage: `USER root`, chown 1001:0, `chmod -R g=u` and `a+rX /app`, then `USER 1001`.
- Frontend: set `API_UPSTREAM`/`BACKEND_URL` to the generated api Service name (nginx crashes with "host not found in upstream" otherwise); `VITE_AUTH_MODE=sso` is a build arg baked at build time.
- Superseded in part (checked 2026-10-05 against main 0.19.0): since 0.16.1 the API listens on 8080 and the web image defaults `API_UPSTREAM=http://fits-api-service:8080`, renders the nginx server block into /tmp (the pod root fs is read-only; the alpha01 approach of a world-writable conf.d crashed there) and sizes workers from the CPU limit. The maintained reference is `docs/OPENSHIFT_GITOPS.md` (by Voravit L., verified against manifest 1.0.28); the literal-FROM / Nexus / repo-root-context / USER rules above are untouched.
- First OCP DEV run of `0.19.0-alpha01` (2026-10-05): the web image is fine, `fits-api` CrashLoopBackOff at `Program.cs:90` because the generated ConfigMap has empty `Authentication__Authority`/`__Audience` (issue #150, manifest 1.0.29-build1). Verified locally in a pod-like container: placeholder https values (`https://adfs.bank.local/adfs`, `api://it-budget`, the examples of docs/DEPLOY_ON_PREM.md) pass the guard and `/health/ready` is 200, but nobody can sign in (mock header gives 403 in Production); `ASPNETCORE_ENVIRONMENT=Development` was not usable as shipped by main 0.19.0 (`/app/seeds/development-users.json` is not in the image, so mock login gives 401; the team docs forbid Development outside a developer machine); dev-ohm alpha02 adds the file and alpha03 also defaults the image to Development, so the DEV namespace needs no manifest change (a ConfigMap/Secret value overrides it). A ConfigMap input change only needs Jenkins CD (new GitOps version), not a new image or tag. The real values come from the identity team (ADFS / TCRB AAA, #78). Likely next failure: `ConnectionStrings__BudgetDb` in Vault / DB reachability.
- Who can edit the OCP config (checked 2026-10-05): the user's GitLab account (O969023) cannot see `gitops/it-admin/fits_manifest` (API 404 for the project and for the group `gitops/it-admin`; the parent group `gitops` is visible), so a ConfigMap edit there needs access granted by the DevOps owner. This Mac has no OCP login (kubeconfig holds only local minikube contexts). Image ENV defaults only work for keys the ConfigMap does not define: a ConfigMap key with an empty value (all `Authentication__*` today) overrides the image default.
- AAA is not involved in the Authority/Audience crash (the user asked on 2026-10-05 whether to "turn AAA off"): it is active only with `Authentication__Provider=AAA` (Program.cs:95-101; default `OIDC` with `Oidc.Enabled=false`, and the ConfigMap has no Provider key), while the guard at Program.cs:88-90 checks the generic JWT keys `Authentication__Authority` and `__Audience`. A Production run with placeholder https values and no AAA keys started fine. Do not set `Authentication__Provider=AAA` before the AAA values exist: Program.cs:110-114 then throws at start unless Aaa Authority and ClientId are set.
- Second OCP DEV blocker (2026-10-05, alpha03 passed the Authority guard; issue #152): `DatabaseInitializer.cs:78` "Database is not at the application's required migration version" means the OCP config has `Database__ApplyMigrations` explicitly false (reproduced locally; an empty string gives a different error, "Failed to convert configuration value ''"), the pod does reach PostgreSQL, and the database is empty or old. A Secret value beats an image ENV, so only Vault/Secret (DevOps) can set it to `true`; then the API creates schema `fits` and applies the 12 migrations itself (the role needs CREATE on the database, or a pre-created schema, or `ConnectionStrings__DbOps`). Next errors to expect: permission denied on CREATE, or "The selected schema allows PUBLIC CREATE" if `Database__Schema` is `public` on PostgreSQL older than 15 (`.env.example` says `public`). Outcome the same day: DevOps said the value was already `true`; the failing start predated the config change, so only a pod restart/re-sync was needed (no repo change). Lesson: Secret/ConfigMap changes reach a pod only at its next container start, so a log can show the previous config.
- Vault `it-admin/dev/int/fits-api` must hold real `ConnectionStrings__BudgetDb` (generated secret was empty).

**Why:** each of these caused a failed Jenkins/AWX run on 2026-10-01/02. **How to apply:** check these before changing Dockerfiles/compose; test locally with `docker build -f <Dockerfile> .` from repo root and an arbitrary-UID run (`--user 1000650000:0 --cap-drop ALL`).
